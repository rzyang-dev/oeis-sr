# 用 11 亿项看 OEIS 的结构指纹

> 产物：`seq_fingerprint` 表（217,960 条）、`scripts/30_fingerprints.py`
> 之前的分析只用了每条序列的前 20–50 项；这一轮开始用 b-file 的长数据。

## 2. 指纹怎么算

每条序列读前 600 项，在尾部（最后 60 个非零项）上计算：

- **log-log 斜率**：`log|a(n)|` 对 `log n` 的斜率 —— 多项式次数估计；
- **log2 比值**：`log2|a(n+1)| − log2|a(n)|` —— 指数底；
- 比值是否随 n 增长 → 阶乘型；
- 尾部周期（p ≤ 12）；
- 位数、零的个数、符号变化次数。

按这些量分成：`polynomial` / `exponential` / `factorial` / `super` / `other` / `zero`。

## 4. 关键信号：增长类几乎决定了能不能被精确求解

在 11,043 条 hard 目标上交叉：

| 增长类 | 解出率 |
|---|---:|
| **exponential** | **36.8%** |
| polynomial | 5.0% |
| factorial | 4.8% |
| other | 4.0% |
| super | 0% |

这是一个接近 10 倍的分层。原因不神秘：

- 指数增长的序列大多属于 **C-finite**（线性递推的解就是指数和），所以 Berlekamp–Massey 直接命中；
- "polynomial 增长"的 hard 目标其实是**多项式增长的组合计数**（分拆、图计数），
  它们不是多项式本身，有限差分永远不收敛；
- 阶乘型需要更高阶的 P-recursive，而我们的 25 项配方对它们不够。

## 5. 这对符号回归意味着什么

拿到一条新序列的几百项，先花毫秒级成本算指纹，然后**分流**：

| 指纹 | 先试什么 | 预期 |
|---|---|---|
| exponential | 线性递推（BM） | 36.8% 命中 |
| polynomial | 有限差分验证是否真多项式；否则转求和/组合模板 | 低 |
| factorial | P-recursive（需要更长窗口/高阶） | 低 |
| super | 直接放弃精确方法 | 0 |

这比"对所有序列跑所有方法"省几个数量级——正是"用信号避免穷举"。

## 6. 局限

- 指纹是启发式的：周期检测有假阳性（例如把增长型序列尾部的重复值误判为周期）；
- 每条只读了 600 项，长周期和大 n 行为可能看不到；
- 还没有在全库上验证"到底有多少序列是严格 C-finite"——那需要每条 200 项拟合 + 200 项验证，
  是下一步。

## 7. 下一步

1. **全库 C-finite 普查**：对 21.8 万条各取 200 项拟合、200 项验证，得到"严格可线性递推"的比例。
2. **真实多项式检测**：对 polynomial 类跑有限差分，区分"真多项式"与"多项式增长"。
3. **把指纹接进形状先验**：增长类 × 公式形状，得到二维的"该走哪条路"决策表。
